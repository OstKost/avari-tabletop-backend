# План улучшения и развития проекта

Дата: 2026-10-02. Объём: завершённый этап «Быстрый поиск и удобная коллекция».

## Основания и результат

Поиск сейчас получает полные детали каждой найденной игры через BGG, чтобы показать отметку о наличии в коллекции. Это добавляет сетевые запросы и записи каталога. Коллекция скрывает ошибки чтения под пустым списком, допускает пустой статус и молча сбрасывает некорректную оценку. Фильтр обновляет список, но оставляет старое выделение вкладки. Для игры без оценки браузер получает значение 0 при допустимом диапазоне 1–10.

Результат этапа: поиск BGG делает только запрос поиска; свою коллекцию можно искать по названию и сортировать; редактирование и удаление показывают корректный результат, сохраняют выбранные фильтры и сообщают об ошибках.

## Работы и критерии приёмки

### A. Быстрый поиск BGG

- Определять наличие игр одним чтением коллекции пользователя и сопоставлением по BGG ID. Не получать детали и не записывать каталог при показе результатов.
- Пустой запрос/выдача не читают коллекцию. Ошибка чтения коллекции не мешает показать результаты BGG.
- Убирать пробелы вокруг запроса, считать минимальную длину в символах; запрос из двух кириллических букв допустим, из одной — отклоняется без обращения к BGG.
- Ожидание ограничения частоты BGG прерывается при отмене контекста.
- Проверки: полная страница и HTMX, правильные отметки текущего пользователя, один `/search` и ноль `/thing`, ошибки, экранирование, отмена контекста.

### B. Поиск и сортировка своей коллекции

- `GET /collection` принимает `status`, `q`, `sort`; `sort`: `newest` (по умолчанию), `name`, `rating`.
- `q` ищет подстроку названия без учёта регистра, включая кириллицу; работает совместно с фильтром статуса.
- Сортировка: новые добавления первыми; название по возрастанию; личная оценка по убыванию, игры без оценки в конце. Равенства разрешаются стабильно.
- Выполнять обработку в service на основе существующего `ListByUser`; интерфейс репозитория и схема БД сохраняются.
- Полная страница и HTMX используют один фрагмент с контролами и списком: значение поиска, сортировки и активный статус соответствуют URL. GET-форма и ссылки доступны обычной навигации и с клавиатуры.
- Пустая коллекция, отсутствие совпадений и ошибка загрузки имеют разные сообщения. Ошибки не выдаются за отсутствие игр.

### C. Надёжное редактирование коллекции

- Add/Update принимают только `owned`, `wishlist`, `played`; пустой статус разрешён только для чтения всех записей. Add без статуса по HTTP сохраняет существующее значение по умолчанию `owned`.
- Оценка — пустое поле или целое 1–10. Некорректная оценка отклоняется до записи, существующая оценка не сбрасывается.
- Сохранять различимые ошибки: неверный ввод — 400, дубль — 409, отсутствующая запись — 404, сбой хранилища — 500. Дубль и сбой не показываются как успешное добавление.
- HTMX показывает понятное сообщение об ошибке и сохраняет редактор при неудаче; успешная запись/удаление обновляет список с текущими фильтрами и пустое состояние после последнего удаления.
- Отсутствующая оценка отображается пустым полем. Заметки с кавычками, переносами и HTML безопасно передаются в редактор.
- Проверки: валидация без вызова записи, очистка оценки пустым значением, принадлежность записи текущему пользователю, успешные и неуспешные HTTP/HTMX ответы, реальные встроенные шаблоны.

### D. Документация и интеграционная проверка

- Добавить README с запуском, конфигурацией существующих провайдеров, новыми возможностями коллекции и корректными условиями тестирования.
- Выполнить узкие проверки, обычные Go-тесты, vet и сборку. Проверить изменённый интерфейс в доступном браузере, включая клавиатуру и мобильную ширину; записать фактический охват и ограничения.
- В конце обновить этот план статусом каждого блока и результатами команд.

## Оркестрация и владение

Сначала координатор сохраняет план и фиксирует контракты. Затем два агента работают параллельно, в общих файлах не пересекаются:

- Агент A: `internal/handler/game_handler.go`, новые тесты поиска; `internal/service/game_service.go` и его новые тесты; `internal/bgg/client.go`, тесты отмены BGG.
- Агент B: `internal/handler/collection_handler.go`, новые тесты коллекции; `web/templates/pages/collection.html`, `web/templates/partials/collection_list.html`, `web/templates/partials/collection_card.html`. Если нужен общий показ ошибок HTMX — согласовать с координатором изменение base/toast/add_button.
- Координатор: `internal/service/collection_service.go`, новый файл обработки поиска/сортировки и тесты service; `docs/DEVELOPMENT_PLAN.md`, `README.md`, общие проверки, интеграция и проверка браузером. После завершения агентов — взаимная проверка отдельных блоков без редактирования.

Все участники читают применимые AGENTS.md, сохраняют существующие файлы и изменения коллег. Git в каталоге отсутствует; commit/push/deploy в этап не входят.

Контракт service: `CollectionBrowseOptions{Status model.CollectionStatus, Query string, Sort string}`, `Browse(ctx, userID, options) ([]model.CollectionWithGame, error)`. Различимые ошибки: `ErrInvalidCollectionStatus`, `ErrInvalidCollectionRating`, `ErrInvalidCollectionSort`; дубль сохраняет `repository.ErrDuplicate` через `%w`. Существующий `List` остаётся доступен поиску BGG.

Все новые Go-проверки запускались с `GOCACHE=/private/tmp/tabletop-ai-go-cache`: системный кэш находится за пределами доступного для записи каталога. HTTP-заглушки требовали разрешённого запуска локальных портов.

- `go test ./internal/service -run 'TestCollection' -count=1` — PASS.
- `go test ./internal/handler ./internal/service ./internal/bgg -run 'TestGameSearch|Test.*Cancel' -count=1` — PASS.
- `go test ./internal/handler -run 'TestCollection|TestRenderer|TestNewRenderer' -count=1` — PASS.
- `go test ./internal/service ./internal/bgg -run 'TestGameFetchBGGAbsenceAndStaleFallback|TestGetGame_NotFound' -count=1` — PASS.
- Итоговое `go test ./... -count=1` после исправлений — PASS.
- Итоговое `go vet ./...` — PASS; `go build ./cmd/server ./cmd/seed` — PASS.
- `gofmt -l` для всех 13 затронутых Go-файлов — пустой вывод.

Для проверки хранения создан отдельный временный PostgreSQL в `/private/tmp/tabletop-ai-verify-pg`, порт 55432, база `tabletop_verify`. Приложение запущено на порту 18080 с отдельным векторным каталогом в `/private/tmp`; миграции применились. Команда `python3 /private/tmp/tabletop-ai-verify-http.py` — PASS. Сценарий через реальные HTTP-маршруты и PostgreSQL подтвердил:

- совместный поиск на кириллице и статус, сортировку, полную страницу и HTMX-фрагмент;
- пустую коллекцию другого пользователя и запрет изменения/удаления чужой записи (404);
- неверную оценку (400) с сохранением предыдущих оценки и заметок;
- сохранение статуса, удаление оценки пустым полем и экранирование заметок;
- повторное добавление (409), исчезновение записи из прежнего фильтра;
- успешное удаление и пустое состояние после последней записи.

Временные сервер и PostgreSQL остановлены после проверки. Пользовательская база и правила не использовались.

Ограничения: Playwright E2E, JavaScript/HTMX в живом браузере, клавиатура и мобильный экран не проверены из-за таймаутов разрешения браузера. Реальные BGG/LLM/Ollama не вызывались; они заменены локальными заглушками в Go-тестах. Риск, требующий следующей браузерной проверки: визуальное обновление списка и состояния Alpine после сохранения/ошибки. Поиск и сортировка коллекции обрабатывают загруженный список в памяти; для очень больших коллекций потребуется перенос фильтрации/сортировки и пагинации в repository.
